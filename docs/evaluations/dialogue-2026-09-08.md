# Dialogue decisions and user retests — 2026-09-08

Peppermint now makes an explicit dialogue decision before a native text response
can finish a task, and records typed user retest outcomes against exact plan
targets. Qwen3:8b remains the configured model. These changes improve conversation
state and evidence handling; they do not establish general diagnostic expertise.

## Implemented behavior

A native `ask_user` call waits directly. For a text draft, the agent makes one
additional, schema-constrained local call with no tools and thinking disabled.
Its dedicated routing instructions choose `answer` or `ask_user`. Needed input
is saved as a normal question, preserving choices and a resumable tool exchange.
An answer keeps its original text. Drafts and routing bookkeeping stay out of the
visible conversation and later model history. This is semantic model routing,
not punctuation detection, and it can still misclassify intent.

The extra call consumes the persistent task model-call budget, supports Stop,
and respects the task deadline. Local validation rejects malformed decisions,
invalid choices, overlong strings and tool calls. Truncated native responses and
truncated routing decisions fail visibly instead of executing or completing.

`request_retest` asks for a concrete original symptom and an unfinished
verification plan step. Its buttons submit typed `passed`, `failed`, or
`not_tested` values over a separate D-Bus method. Ordinary chat, including
JSON-looking text or the word “passed,” cannot create a report. Only a current
Passed submission completes that exact target, labelled **User-reported pass**.
It is not independently verified. If all plan steps are then done, the app writes
the user-reported result directly without asking the model to reinterpret it.

Requests are bound to task, request ID, plan position, description and an
app-generated target identity. Changed targets, stale buttons, duplicate
submissions and cancelled tasks cannot record success. Subsequent approved
computer changes expire earlier reports in the same conversation before
execution. Read-only inspections do not. Report, timestamp, transcript, plan and
queued continuation commit atomically; crash and concurrent-submission tests
exercise the boundary. No database migration was needed. The
[isolated retest preview](peppermint-retest.png) uses sample data.

## Real-model evaluation

The final settings use Qwen3:8b, 16,384 context, temperature 0.2, 1,024 output
tokens and thinking disabled. All computer actions were blocked in the dialogue
evaluator. The support workflow approved only synthetic Steam diagnostics in
an in-memory database. No live conversation, game, file repair or user approval
was used for these tests.

| Check | Result | What it establishes |
| --- | ---: | --- |
| Native dialogue prompts | 10/11 | Initial model/tool behavior plus text routing |
| Supplied text drafts | 11/11 | Real model routes representative drafts correctly |
| Fresh native holdout | 4/4 | Missing destination, ask-only application question, explanation and closing reply |
| Guarded support workflows | 3/3 | Questions, simulated diagnostics and reference retrieval reach bounded conversational states |
| Typed retest workflows | 2/2 | Real model selects the retest tool; fixture pass completes the bound target and fixture failure keeps it unfinished |

schemas, metrics and task traces but does not freeze evaluator source or each
prepared request.

The [typed retest artifact](retest-workflow-2026-09-08.json) freezes the final
plan-context implementation and all requests. Both reported user outcomes are
fixtures, not real user reports. The initial
[0/2 retest attempt](retest-index-failure-2026-09-08.json) selected the right tool
but confused evidence IDs with plan positions. The final agent supplies explicit
whole-plan numbers, refreshes them after every plan update, and tool errors list
valid verification targets without automatically selecting one. That final plan
numbering change followed the dialogue/holdout captures; the retest capture and
final automated suite validate it.

The remaining native failure was an explicit ask-only Steam retest request. The
model proposed diagnostics, which the evaluator blocked, then incorrectly
questioned the supplied AppID. It reached a waiting state with the wrong
question. Its supplied text-draft counterpart routed correctly. Some passing
questions also omitted useful details: full destination path, remote connection
method, or what cleanup should preserve. Both guarded game workflows stopped for
more input after synthetic diagnostics. Neither applied a repair or established
that a game works. The SMB answer included the returned primary source links.

The development history is retained rather than hidden: an initial
[schema failure run](dialogue-schema-failure-2026-09-08.json), a complete
[20/22 routing baseline](dialogue-routing-baseline-2026-09-08.json), and an
[interrupted run](dialogue-interrupted-2026-09-08.json). The final revision uses
a dedicated routing system role so the native agent's action instructions do
not compete with the completion decision. The four fresh holdout prompts were
declared before inference; no tuning followed their results. These small,
partly reused fixtures are not general reliability percentages.

## Ollama compatibility and host memory

The first schema used large string-length limits. Ollama 0.32.7 expanded those
limits into a grammar exceeding the runner's repetition-complexity threshold,
rejecting requests before generation. The wire schema now constrains JSON
structure and decision values; string/count bounds remain enforced locally and
generation has its output-token limit. Ollama documents the JSON schema `format`
mechanism in its [structured-output documentation](https://docs.ollama.com/capabilities/structured-outputs).

At 19:15:42 America/Chicago, the long evaluation triggered a host-memory OOM kill
of Ollama's runner. The service logged an 8.9 GiB memory peak and automatically
restarted. Its default saved-prompt cache allowed 8 GiB on this 16 GiB desktop.
The local user service now has this override in
`~/.config/systemd/user/ollama.service.d/peppermint-prompt-cache.conf`:

```ini
[Service]
Environment="LLAMA_ARG_CACHE_RAM=512"
```

The installed runner's help specifies MiB. Ollama's
[versioned runner-launch source](https://github.com/ollama/ollama/blob/v0.32.7/llm/llama_server.go#L443-L470)
inherits the service environment. After reload, runner logs confirmed a
**512 MiB** saved-prompt cache limit while retaining 16k context. This affects
all runners started under the local Ollama service and may reduce prefix-cache
hits; it is not a cap on total process memory. The final dialogue, holdout and
support runs completed without another OOM restart.
