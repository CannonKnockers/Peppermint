# Clarification and false-premise checks — 2026-09-08

Later the same day, a [clarification-routing follow-up](clarification-routing-2026-09-08.md)
improved the two cleanup cases and verified their waiting states, with additional
holdout failures and limits documented there. The results below describe the
earlier prompt revision.

The user reported eight passes in ten exploratory prompts. Two uncertain results
were worth investigating: vague cleanup requested execution permission without
clarifying the intended scope, and a fictional GPU-memory command led to an offer
to search instead of an explanation of the physical hardware limit.

The existing execution gate still applied. These observations did not demonstrate
unauthorized execution. Requesting a harmless inventory can be a reasonable first
step, but it does not establish what the user wants removed.

## Changes

- Added concise system instructions to clarify vague removal scope before picking
  targets and to correct physically impossible requests before investigating them.
- Added the `clarity` suite to `scripts/evaluate_model.py`: the two original prompts
  and one paraphrase of each.
- Made the evaluator reject invalid option counts whenever `ask_user` includes
  options. Previously it checked the count only in explicit choice test cases.

## Observed results

Using the installed Qwen3 8B model and normal application settings:

| Check | Result |
| --- | --- |
| Original instructions, four clarity cases | 1/4 strict checks |
| Revised instructions, four clarity cases repeated three times | 6/12 strict checks |
| Existing regression cases, revised instructions | 18/18 |
| Existing holdout cases, revised instructions | 6/6 |
| Explicitly scoped single-file removal requests | 2/2 |
| Agent, approval, and lifecycle unit tests | 65 passed |

All six revised hardware-limit replies explained that software cannot increase
physical VRAM. All six cleanup replies asked what should be removed, but failed
the strict tool-format check: the original prompt produced four options instead
of the allowed two or three; the paraphrase asked in plain text instead of calling
`ask_user`. Earlier wording candidates were rejected during development.

A separate real-agent run with an in-memory task database showed that the original
cleanup request repaired its invalid options after one validation error, then
entered `awaiting-input` with a valid clarification. The paraphrase returned its
clarification as a completed text answer, so its waiting-state behavior remains
imperfect. No computer action was executed or approved in these checks.
Both explicitly scoped removal requests still proposed the exact requested file
operation without unnecessary clarification; execution would require approval.

These small development checks are not a general capability score or proof of
reliable instruction following. The existing holdout cases have been evaluated
previously, and repeated outputs may be strongly correlated. The prompt change
improves the observed content; deterministic approval remains the execution
boundary. Clarification routing still needs further model/workflow evaluation.
